# Performance techniques

The stick has one ARM1176 core and 55 MB of RAM. A frame at 59.94 Hz has a budget of about 16.7 ms, shared by emulation, video and audio. Each technique below states the principle behind it.

## Pacing

**Let the TV retrace be the clock.**
Swap the buffer, call `0x6402`, then `0x6407`. The wait ends at the frame interrupt, so game speed follows the screen exactly. Principle: there can be only one master clock, and the screen is the one the player sees.

**Never sleep for fine timing.**
`usleep` has a resolution of 10 ms because the kernel runs at HZ=100. Any delay rounds up to the next tick. Principle: use the hardware event, or a busy wait on the clock when no event exists.

**Keep audio non-blocking.**
A blocking audio `write` sleeps in steps of 10 to 20 ms inside the driver. If audio holds the pacing, frame times wobble even when the average looks correct. Principle: the average frame rate says nothing about cadence, so look at the minimum and maximum intervals.

**Correct drift with rate control, not with waiting.**
The core's rate and the TV's rate never match exactly. The runner reads the queue with `GETODELAY` and adjusts the resampling ratio by up to +/-0.8 % toward a target of 2000 audio frames. Principle: a change that small is inaudible, while an underrun is not.

**Fall back when the retrace wait is not usable.**
If the average wait over 300 frames is below 0.5 ms or above 30 ms, the runner paces by the clock with a busy wait. Cores outside 58 to 62 Hz also use the clock (`plat_disable_retrace`), because tying them to the retrace would change game speed. Principle: game speed must stay correct even when smoothness cannot.

## Disk

**No card writes during a game.**
Repeated `fsync` on the SD's FAT32 freezes the picture for many frames. Statistics go through a 16 KB buffered log with no flush and reach the card on exit. Controller packet logging is off during a game. `step()` with `fsync` is reserved for risky startup steps. Save states use `fsync` only while paused. Principle: slow I/O belongs where the player cannot see it.

## Video

**Never read from chunkmem.**
Reads from video memory are very slow. Build the line in normal memory and copy it with `memcpy`. Principle: treat video memory as write only.

**Use integer scaling.**
Build one line, writing 2 pixels at a time with a `uint32`, then `memcpy` it to the other k-1 lines. Principle: a scale that repeats work can reuse it, and an exact multiple needs no per-pixel table.

**Draw in RGB565.**
It is the panel's native format, so nothing needs converting at the end of the frame.

**Redraw only what changed.**
Cache the background, fill the core of rectangles a line at a time, and skip the frame when nothing moves. Drive animation by elapsed time (`dt`), not by frame count, so it keeps its speed at any frame rate. Principle: an idle menu should cost almost no CPU.

## Precomputation

**Compute on the PC whatever never changes.**
Music, effects and the Aero background are generated by `tools/gen_audio.c` into `retro/audio/`. The stick only reads them. Principle: live synthesis or a large background built at boot takes time the device does not have, and a file on the card costs almost nothing.

## Emulation

**Pick the core for the hardware, not for accuracy.**
QuickNES fits the frame budget where FCEUmm does not. The selected cores for weak ARM use assembly CPU cores or a dynamic recompiler: snes9x2002 (ARM assembly), picodrive (Cyclone 68000, DrZ80), RACE (DrZ80), gpsp (ARM dynamic recompiler).

**Use compiler flags that match the CPU.**
Cores build with `-O3 -fomit-frame-pointer -fno-strict-aliasing` and `-mcpu=arm1176jzf-s -mfpu=vfp -mfloat-abi=softfp`. The menu needs `-mcpu=arm1176jzf-s` as well.

**Skip drawing before skipping sound.**
The runner skips at most 2 frames in a row, when the clock falls more than 2 ms behind or the audio queue drops below a quarter of its target. snes9x2002, gpsp and picodrive use libretro's `frameskip=auto`: the runner reports the queue through `SET_AUDIO_BUFFER_STATUS_CALLBACK` and the core stops drawing when it runs low. Principle: a dropped frame is less noticeable than broken audio.

**Lower the audio load when a core allows it.**
Core options live in the options table in `src/runner.c`, for example `fceumm_sndrate_hint=32KHz`.

## Memory

**Give the game the whole machine.**
The menu exits before a game runs, and `retro/init` launches the game in its place.

**Page large ROMs.**
gpsp is built with `ROM_BUFFER_SIZE=8` and `SMALL_TRANSLATION_CACHE`. When a core sets `need_fullpath`, the runner passes the path and does not load the ROM into RAM.

## Tuning knobs

- Choppy audio: raise `QUEUE_TARGET` in `runner_audio.c` or the fragments in `plat_audio_init`.
- Audio lagging behind the picture: lower them.
- `STICK_VSYNC=0` turns off the retrace wait, for comparison.
- `STICK_CLOCK_TEST=1` logs the real duration of `usleep` and of 120 swaps with retrace wait.

## Rules for any new code on the stick

- Draw in RGB565 and at integer scale whenever possible.
- Do not use `usleep` for fine pacing.
- Pacing comes from the retrace, never from the audio write.
- Audio is always non-blocking, with rate control from the queue.
- No `fsync` and no frequent writes to the card during a game.
- Read the per-part timings in the logs before optimizing (see CARD-TESTING.md).
- Any technique must hold for every game on every system.
